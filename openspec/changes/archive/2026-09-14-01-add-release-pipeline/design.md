## Context

See proposal.md - Why. Current state that shapes the approach:

- **Local build path** (README "Building it yourself"): freeze the sidecar in a venv with `build_sidecar.py`, then stage it as `src-tauri/binaries/transcriber-sidecar-<triple>`, run `fetch_sidecar_resources.py`, run `cargo tauri build`, and finally `build_portable.py`. CI repeats the same steps, natively on each OS. PyInstaller can't cross-compile, so there's no alternative to native builds.
- **Version** lives in two places: `src-tauri/tauri.conf.json` (`version`, which Tauri stamps into installer filenames and metadata) and `src-tauri/Cargo.toml`. Both are `0.1.0` today.
- **Model license**: `src-tauri/resources/model/LICENSE.txt` is force-tracked in git despite the `src-tauri/resources/**` ignore rule, so a CI checkout already has it. `fetch_sidecar_resources.py` downloads the weights into the same directory next to it.
- **Python**: the local venv runs 3.14.
- **macOS GUI live capture is still disabled** (`src/main.js` platform gate, `desktop-gui` "Graceful macOS degradation"). That matters for `03`, not here.
- **The repository is public**, so hosted runners cost nothing.

## Goals / Non-Goals

**Goals:**
- One workflow file that builds every release artifact. `02` and `03` extend it with their legs.
- Linux artifacts that install cleanly on Debian/Ubuntu and Fedora/openSUSE, with that proven in CI rather than assumed.
- A CLI archive that works offline out of the box.

**Non-Goals:**
- Code signing, an auto-updater, or changelog generation.
- Replacing the local WSL build path. It stays as the development path.
- Build caching (see Decision 9).
- Continuous integration on every push. The workflow only runs on tags and on manual dispatch.

## Decisions

### 1. One workflow, a preflight job, and draft releases uploaded with the `gh` CLI

```
push tag v*  ──▶ preflight (ubuntu): version check → provenance URL check → gh release create --draft
                     │
                     ├─▶ linux leg    (this change)
                     ├─▶ windows leg  (02)            each: build → smoke test → package →
                     └─▶ macos leg    (03)                  gh release upload <tag> --clobber
workflow_dispatch ──▶ same legs, no preflight release step; outputs go to actions/upload-artifact
```

- **Draft, not published directly.** Nothing public exists until a maintainer has looked at the draft. A failed leg leaves a draft that can be deleted, rather than a half-empty public release.
- **Plain `gh`, not `tauri-action`.** `tauri-action` only knows about Tauri bundles. The portable zips and CLI archives come from `build_portable.py`, so they would have to be uploaded by hand anyway. `gh` is preinstalled on every runner. The workflow needs `permissions: contents: write`.
- **Rejected: release-please or automatic version bumps.** One manual version bump per release is cheaper than configuring either.

### 2. Native builds per OS; Linux on `ubuntu-22.04`

The glibc of the build host sets the oldest system the AppImage and the frozen sidecar will run on. 22.04 ships glibc 2.35. Debian 12 has 2.36, openSUSE Leap 15.6 has 2.38, and current Fedora and Tumbleweed are newer, so all target distros are covered. When GitHub retires the 22.04 image (around 2027), moving to 24.04 drops Debian 12. That's an accepted, later decision.

### 3. Tauri CLI from npm in CI

The workflow runs `npx --yes @tauri-apps/cli@<pinned>` instead of `cargo install tauri-cli`. It's the same open-source CLI, shipped prebuilt through npm, which saves the roughly 18-minute cold compile recorded on the Mac build. Node is preinstalled on runners. Pin it to the same minor version as the `tauri` crate in `Cargo.lock`. Local builds keep using `cargo tauri`.

### 4. `.rpm` dependencies declared by shared library, not package name

Fedora names the WebKitGTK package `webkit2gtk4.1`; openSUSE names it `libwebkit2gtk-4_1-0`. A package-name dependency can only satisfy one of them. RPM also accepts library capabilities, which both `dnf` and `zypper` resolve to whatever package provides them:

```json
"linux": { "rpm": { "depends": ["libwebkit2gtk-4.1.so.0()(64bit)", "libgtk-3.so.0()(64bit)"] } }
```

Confirm the exact list during implementation against `ldd` output for the built `transcriber-gui`. `.deb` dependencies are generated by Tauri and need no config.

### 5. `build_portable.py` also emits the CLI archive, and every file name carries version and platform

One invocation per leg produces both the GUI portable artifact and the CLI archive, so the workflow doesn't grow a second assembly step.

```
transcriber-cli_<version>_<os>-<arch>/
├─ transcriber[.exe]      ← dist/<system>/transcriber-sidecar[.exe], renamed
├─ model/                 ← src-tauri/resources/model/ (LICENSE.txt included, .cache/ excluded)
├─ <launcher script(s)>   ← linux-start-transcription.sh | win-start-transcription.bat + transcribe_file.bat | mac-start-transcription.sh
└─ LICENSE, THIRD-PARTY-LICENSES.txt, SOURCE-PROVENANCE.txt
```

- Windows gets `.zip`; Linux and macOS get `.tar.gz`, because `zipfile` doesn't reliably preserve the executable bit and `tarfile` does.
- The version is read from `tauri.conf.json`, so it can't drift from the GUI artifacts.
- The portable GUI files get versioned names too (`Transcriber_<version>_windows-x64.zip`, `Transcriber_<version>_macos-arm64.zip`). Tauri-built bundles (`.AppImage`, `.deb`, `.rpm`, NSIS, `.dmg`) are already versioned.
- The launcher-file mapping for all three platforms lives here as data. The script edits themselves happen in each platform's change.

### 6. The standalone CLI finds its bundled model on its own

In `transcriber.py`: when running frozen (`sys.frozen`), `--model-path` is absent, `--model` is `base`, and `<dir of sys.executable>/model/model.bin` exists, use that directory as the model path.

- **Frozen only**, because a source checkout has no bundled model, and a relative-path lookup there would only surprise people.
- **`base` only**, because that's the size bundled. `--model small` keeps downloading as before.
- **The GUI is unaffected.** It always passes `--model-path`. In every GUI layout the model sits at `resources/model`, never at `model/` next to the sidecar (and `.deb`/`.rpm` put the sidecar in `/usr/bin`), so it can't accidentally match.
- **Rejected: launchers pass `--model-path`.** A plain `transcriber --file x` would still download, which would make bundling the model pointless.

### 7. Smoke test with a generated WAV and no fixture file

A few lines of stdlib `wave` write two seconds of silence. The test then runs `<sidecar> --file silence.wav --model-path src-tauri/resources/model`, expecting exit 0 and an output file, and `<sidecar> --list-devices-json`, expecting exit 0 and valid JSON (an empty list is acceptable, as in `linux-sidecar-build`). Together these prove the binary starts, the model loads, and PyAV decodes. That covers the failures seen so far: the missing VAD asset, the FlexiBLAS abort, and the multiprocessing relaunch.

### 8. Container install checks in the Linux leg

After packaging, the leg installs each package in throwaway containers: `debian:stable` and `ubuntu:24.04` with `apt install ./x.deb`, and `fedora:latest`, `opensuse/leap:latest`, and `opensuse/tumbleweed` with `dnf` or `zypper install ./x.rpm`. The check is only that the install succeeds, which proves the dependencies resolve. GUI launch stays a manual check on real hardware. It adds a few minutes, and it's the only way to verify Decision 4 without owning each distro.

### 9. No caching at first

`ponytail:` no cache for Rust, pip, or the model. Releases are rare, and a cold leg costs minutes, not money. Add `Swatinem/rust-cache` or `actions/cache` if waiting for release builds becomes annoying.

### 10. Provenance check skips templated URLs

`SOURCE-PROVENANCE.txt` contains one templated URL (`.../ffmpeg-{platform}.tar.gz`). The check extracts every URL, skips any containing `{`, and requests each of the others with `curl -fsSL --retry 2 -r 0-0 -o /dev/null`. It uses a ranged GET rather than `-I`, because some hosts reject HEAD requests. This automates step 1 of README's "Before publishing a release". Step 2 (re-deriving provenance after a PyAV bump) stays a human step in the release checklist.

### 11. Launcher fallback in the shell script

`linux-start-transcription.sh` checks `[ -x "$SCRIPT_DIR/transcriber" ]` and, if true, builds `CMD=("$SCRIPT_DIR/transcriber" --live ...)`; otherwise it uses the current Python path. The command is still printed from, and executed as, the same array.

## Risks / Trade-offs

- **[Risk]** A needed wheel (ctranslate2, onnxruntime, av) has no Python 3.14 build on some runner → pin that leg's `setup-python` to the newest version that has wheels, and record it in the workflow file.
- **[Risk]** The `.rpm` library capability names are wrong or incomplete → the container checks fail the leg before anything reaches a release.
- **[Risk]** Spec runs ahead of implementation. The `teams-launcher` and CLI-archive requirements cover Windows and macOS, but `02` and `03` implement them. This is the same precedent as `remove-installer-packaging` and `05`/`06`. The period between archiving `01` and `02`/`03` is temporary and known.
- **[Trade-off]** CI's Linux build (Ubuntu, glibc 2.35) differs from local Fedora builds. Released artifacts come from CI, and local builds are for development.
- **[Trade-off]** Every release is roughly 10 assets of about 300 MB each. That's under GitHub's 2 GB per-asset limit, and there's no practical total limit.

## Migration Plan

The first real run can be the tag `v0.1.0`, which matches the current version. If it's only a test, delete it afterwards with `gh release delete v0.1.0 --cleanup-tag`. To roll back, delete `.github/workflows/release.yml`; local builds don't depend on it.
