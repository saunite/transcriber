  **Verified for real**, on this WSL machine (WSLg, `DISPLAY=:0`/`WAYLAND_DISPLAY=wayland-0`). Ran the AppImage directly: `pstree` showed `transcriber-gui` plus WebKit helper processes, and a brief `transcriber-sidecar --list-devices-json` call at ~t+2-4s — the device-picker population from the "Device selection UI" requirement, not a session sidecar; consistent with existing app behavior, not a build defect. No GUI-automation tooling available (no xdotool/ydotool) to drive drag-and-drop, so — matching the exact methodology `remove-installer-packaging` task 5.2 used — extracted the AppImage (`--appimage-extract`) and ran the bundled `usr/bin/transcriber-sidecar` directly against `usr/lib/Transcriber/resources/model` with a synthetic WAV: exit 0, correct summary (`Duration: 2.0 seconds`, language detected, `Segments: 0` — correct for a pure tone with no speech), transcript file written.

  **Real anomaly found, not a build-mechanism bug**: a spawned subprocess printed an `argparse` usage error (`unrecognized arguments: -B -S -I -c from multiprocessing.resource_tracker import main;main(15)`) — Python's `multiprocessing.resource_tracker` re-execing the frozen binary with interpreter-style args its own CLI doesn't parse. Didn't block the transcription (which succeeded regardless). Root cause: this sidecar was frozen under **Python 3.14.4** (only version available on this machine), while CI's previously-verified build used **3.11** (`build-gui.yml`'s `python-version: "3.11"`) — plausibly a `multiprocessing`/PyInstaller behavior change between those versions. Not fixed here (out of scope for this change, which verifies the *build mechanism*, not sidecar internals) — flagged for a follow-up if Python-version parity with CI matters.
